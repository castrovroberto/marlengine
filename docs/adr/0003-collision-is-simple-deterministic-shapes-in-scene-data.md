# Collision is simple deterministic shapes in scene data

Entities touch things through a **Collider** component: an axis-aligned box or a circle, either **solid** (blocks movement) or a **trigger** (blocks nothing, only reports overlaps). Tilemap cells can be solid through a field on `Tilemap`. Nothing here is physics: there are no forces, velocities or bodies, only positions that behaviors already write to `Transform`, checked against shapes. The engine stops moving entities at solids as part of the fixed step and reports which triggers overlap which entities, in a fixed order, so a scene, a seed and an input recording still give the same result (ADR-0002). Interactions and dialog (M8) read the overlaps; they are not designed here.

## The decision

- **Collider component.** `shape` (`box` or `circle`, `OneOf`), `size` (box width and height, world units), `radius` (circle), `offset` (from the entity's `Transform.position`) and `kind` (`solid` or `trigger`, `OneOf`). Every field is written, so the field that does not apply to the shape is ignored; validation requires a positive size for a box and a positive radius for a circle. The component is separate from `SpriteRenderer` and `Transform` because an invisible wall or trigger zone has no sprite. `Transform.rotation` and `scale` do not affect a collider: sizes are in world units. A collider on an entity with no `Transform` does nothing, like a sprite without one.
- **Solid tiles.** `Tilemap` gains a `solid` string: the tile characters that block, for example `"cdef"` (empty means none). A solid tile is a box of `tileSize` placed exactly where the renderer draws it, so what you see is what blocks. Tiles are solid only; a tilemap has no triggers.
- **Stopping at solids.** After an entity's behaviors have run, if it has a solid `Collider` and its position changed during the step (compared with its `PreviousTransform`), the engine resolves the move against every other solid collider and solid tile: x first, then y, each axis stopping flush against what it hits. Moving one axis at a time makes an entity slide along a wall instead of sticking to it. An entity that starts a step already overlapping a solid is not blocked by that solid, so a mis-placed entity can walk out. Resolution happens right after that entity's behaviors and before the next entity's, so what follows an entity in the file (a camera with `Follow`) sees its resolved position. It is part of the order the file already defines, not a component the author has to remember to add after the mover. Entities that did not move are never pushed, so two adjacent walls do not interfere. A moving entity never pushes another.
- **Overlaps.** Once per step, after every entity has run, the engine works out which trigger colliders overlap which other colliders (solid or trigger, never the trigger itself). Solid against solid is not reported: those block. The result is runtime state on the scene, not a registered component: the pairs that overlap, and which of them *entered* and *left* since the previous step, sorted by the creation order of the trigger and then of the other entity. Pairs are identified by entity names. Behaviors on the next step read this through the `BehaviorContext`, so an overlap is seen one step after it happens; an entity that is destroyed or a scene that is loaded again reports its pairs as left, and an overlap that exists when a scene is first loaded reports as entered on the first step.
- **Checksums and recordings.** Overlaps are not hashed and recordings do not change: they are recomputed from positions, which are hashed, so equal checksums still mean equal runs. Colliders are registered components, so their fields are in the checksum, the schema, the writer and hot-reload carry-over like any other. Whatever M8 does in response to an overlap changes registered components, which are covered.
- **Vocabulary.** The shape and kind names follow Hazel and Box2D so a physics engine could be added later: solid is a non-sensor, trigger is a sensor, an entity that never moves is a static body and one that behaviors move is a kinematic body. There are no dynamic bodies.

## Considered Options

- **Box2D (or another physics engine).** Deferred, not rejected (docs/roadmap.md). It adds dynamic bodies, friction and stacking, which a top-down tile world does not need. Its body state would live outside the registry, so checksums, hot-reload carry-over and fail-soft loading all get harder, and its results are not guaranteed to match across platforms. Revisit if a game needs real physics; the shape and kind vocabulary above maps onto it.
- **Fields on `Transform` or `SpriteRenderer` instead of a component.** Rejected: an invisible wall or a trigger zone would need a sprite, and a component is the unit the registry, schema and an AI work with.
- **A tile-cell collider list or a separate collision layer in the tilemap.** Rejected for now: a string of solid characters is one line in the file, is checked against the same characters the rows use, and needs no second grid to keep in step. A tile that is solid in one place and not in another would need the second grid; reconsider then.
- **Resolving all solids in one pass after every entity has run.** Rejected: a camera that follows the player would use the position from before the wall stopped it and jitter against walls. Resolving right after each entity keeps "order is part of the file".
- **Stopping by reverting to the previous position.** Rejected: it leaves a visible gap of up to one step of movement and sticks to walls instead of sliding along them.
- **Overlaps as a registered component per entity.** Rejected: it would put derived data into scene files, the writer and the checksum, and make a saved scene differ from the one that was loaded.
- **Rotated boxes, polygons, continuous collision, layers and masks.** Out of scope; each can be added later as new fields or a new `shape` value without changing the above.

## Consequences

- **Limits.** There is no continuous collision: an entity that moves further in one step than the thickness of what it should hit can pass through it. At the Sandbox's speeds that is far from happening; scene authors keep colliders and speeds in that range, and `marle-scene simulate` can show when something got through.
- **Order matters.** Between two moving solid entities, the one earlier in the file is resolved first against the other's position at that moment (its new position if it has run, its old one if not). That is deterministic and a result of the file's order, as for behaviors.
- Collision needs no window or GL context, so it runs headless in `Simulation::Step` and in `marle-scene simulate`.
- All of it is arithmetic on floats in a fixed order, with no clock, no unseeded randomness and no unordered iteration: pairs are visited in creation order. The determinism promise stays as ADR-0002 states it, per build and platform.
- The renderer can draw collider outlines for debugging with `DrawLine` and `DrawCircle` (M7); that is drawing only and does not touch the simulation.
- Implementation follows in M7: the `Collider` component, solid tiles, resolution in `Simulation::Step`, overlap events, the Sandbox overlay and `marle-scene simulate` summary, and determinism tests.
